LAB 2 REPORT
AArch64 Bare-Metal Firmware on QEMU
From QEMU machine discovery to ELF loading, CPU execution, stack initialization, and UART concepts
1. Executive Summary
Lab 2 moved the work from Lab 1's AArch64 Linux user-space execution into bare-metal firmware execution. Instead of running an AArch64 application under Linux, the lab used QEMU's system emulator to create a virtual ARM machine containing a Cortex-A53 CPU, RAM, and memory-mapped devices.
A minimal AArch64 firmware image was built from assembly. The source was assembled into a relocatable ELF object, linked with a custom linker script into an executable ELF, loaded by QEMU, and debugged instruction-by-instruction with GDB. The firmware was deliberately small so that source code, machine instructions, memory addresses, the ELF entry point, CPU registers, stack initialization, and UART hardware could be understood as one connected system.
The principal artifact was boot.elf. Its entry point and _start symbol were linked at 0x40000000. QEMU loaded it, and GDB confirmed that the Cortex-A53 began at 0x40000000. The firmware then initialized SP to 0x5ff00000. The PL011 UART at 0x09000000 was identified as the next memory-mapped hardware interface.
2. Objectives
•	Understand qemu-system-aarch64 versus qemu-aarch64.
•	Understand the QEMU virt machine, CPU, RAM, UART, and Device Tree.
•	Build a minimal AArch64 bare-metal program without Linux, libc, or an application runtime.
•	Understand assembly -> object ELF -> executable ELF.
•	Understand how a linker script determines placement and the entry point.
•	Load the ELF into QEMU and inspect CPU execution with GDB.
•	Understand stack initialization and memory-mapped I/O.
•	Build the foundation for later TF-A boot-stage and secure-boot analysis.

QEMU 10.2.1 was available at /usr/bin/qemu-system-aarch64. This confirmed that machine-level AArch64 emulation was available.

5. Discover the Virtual Machine and CPU
qemu-system-aarch64 -machine help
qemu-system-aarch64 -cpu help
The machine list showed virt-10.2 and its virt alias. The CPU list included cortex-a53.
qemu-system-aarch64 \
    -machine virt \
    -cpu cortex-a53 \
    -m 512M \
    -nographic
This verified that QEMU could instantiate the virtual machine. With no firmware payload, there was no useful guest program to execute. The important point at this stage was machine creation, not application output.
6. Inspect QEMU Machine Options
qemu-system-aarch64 -machine virt,help
qemu-system-aarch64 -machine virt,help | grep -E "firmware|secure|kernel"
qemu-system-aarch64 --help | grep -E -- "-bios|-pflash|-drive|-kernel|-machine" 
The machine options exposed firmware, kernel, secure-mode, memory, and other configuration options. QEMU also contained EDK2 AArch64 firmware metadata under /usr/share/qemu/firmware. UEFI was intentionally not used because the purpose was to understand the smallest bare-metal path first.
7. Generate and Inspect the Device Tree
qemu-system-aarch64 \
    -machine virt \
    -machine dumpdtb=virt.dtb \
    -cpu cortex-a53 \
    -m 512M

ls -lh virt.dtb
file virt.dtb
The generated virt.dtb was about 1.0 MB and identified as a Device Tree Blob version 17. The DTB is a machine description generated by QEMU.
DTC was then installed because it was not initially present:
sudo apt update
sudo apt install device-tree-compiler
which dtc
dtc --version
The installed DTC version was 1.7.2.
dtc -I dtb -O dts virt.dtb -o virt.dts
ls -lh virt.dts
head -40 virt.dts
virt.dts provided a readable representation of the QEMU virtual hardware.
8. Determine RAM Layout
grep -n -A12 -B2 "memory@40000000" virt.dts
memory@40000000 {
    reg = <0x00 0x40000000 0x00 0x20000000>;
    device_type = "memory";
};
The RAM begins at 0x40000000 and has size 0x20000000, which is 512 MiB. Therefore the last byte is 0x5fffffff and the exclusive end address is 0x60000000.
RAM base       = 0x40000000
RAM size       = 0x20000000 = 512 MiB
RAM last byte  = 0x5fffffff
RAM end (exclusive) = 0x60000000
9. Determine CPU
grep -n -A25 -B2 "cpus {" virt.dts
The Device Tree described one CPU, CPU 0, compatible with arm,cortex-a53. phandle values in the Device Tree are internal references and were not CPU addresses.
10. Determine PL011 UART
grep -n -i "uart\|serial\|pl011" virt.dts
sed -n '308,320p' virt.dts
pl011@9000000 {
    clock-names = "uartclk", "apb_pclk";
    clocks = <0x8000 0x8000>;
    interrupts = <0x00 0x01 0x04>;
    reg = <0x00 0x9000000 0x00 0x1000>;
    compatible = "arm,pl011", "arm,primecell";
};
The PL011 UART base is 0x09000000 and the region size is 0x1000, or 4 KiB. Its range is 0x09000000 through 0x09000fff. The Device Tree also identified it through serial0 and stdout-path.
grep -n -i "stdout-path\|serial0" virt.dts
The UART was identified before being programmed. This avoided guessing device addresses and established the memory-mapped hardware model.
11. Initial GDB Experiment
qemu-system-aarch64 \
    -machine virt \
    -cpu cortex-a53 \
    -m 512M \
    -nographic \
    -S \
    -gdb tcp::1234
-S pauses the virtual CPU. -gdb tcp::1234 exposes the GDB debugging endpoint.
which gdb-multiarch
gdb-multiarch
(gdb) target remote :1234
gdb-multiarch was installed because the host debugger was x86-64 while the target CPU was AArch64. The first no-payload connection showed PC=0x0 and SP=0x0, with CPSR decoding including EL=1. This was the observed initial state of the deliberately minimal paused setup, not a claim that a normal firmware boot always starts at address zero.
(gdb) info registers
The general-purpose registers were initially zero. This gave a baseline for later observing firmware execution.
12. Create the First Bare-Metal Firmware
nano start.S
.section .text
.global _start

_start:
    mov x0, #0
    b .
.text places the code in the text section. .global makes _start visible to the linker. _start is the entry symbol. mov x0,#0 sets x0 to zero. b. branches to the current instruction and therefore loops forever. There is no Linux, libc, or main().
cat start.S
13. Assemble start.S
aarch64-linux-gnu-gcc -c start.S -o start.o
ls
file start.o
aarch64-linux-gnu-objdump -d start.o
0000000000000000 <_start>:
   0:   d2800000        mov     x0, #0x0
   4:   14000000        b       4 <_start+0x4>
start.o was an ELF 64-bit AArch64 relocatable object. The assembler translated each AArch64 source instruction into a 4-byte machine instruction. Addresses were still section-relative because final placement had not been assigned.
14. Create the Linker Script
nano linker.ld
ENTRY(_start)

SECTIONS
{
    . = 0x40000000;

    .text : {
        *(.text)
    }
}
ENTRY(_start) makes _start the executable entry point. The location counter is set to 0x40000000, matching the beginning of the QEMU RAM region discovered from the Device Tree. The .text sections are placed there.
This demonstrates an important firmware concept: unlike a normal application, bare-metal firmware needs an explicit memory layout suitable for the target machine.
15. Link into boot.elf
aarch64-linux-gnu-ld \
    -T linker.ld \
    -o boot.elf \
    start.o

file boot.elf
aarch64-linux-gnu-readelf -h boot.elf
aarch64-linux-gnu-readelf -s boot.elf | grep _start
The result was an ELF 64-bit AArch64 executable. The ELF header reported entry point 0x40000000 and the symbol table reported _start at 0x40000000.
Entry point address: 0x40000000
_start: 0000000040000000
16. Inspect ELF Program Headers
aarch64-linux-gnu-readelf -l boot.elf
Type   LOAD
Offset 0x10000
VirtAddr 0x40000000
PhysAddr 0x40000000
FileSiz 0x8
MemSiz  0x8
Flags   R E
Align   0x10000
There was one LOAD segment. FileSiz and MemSiz were both 8 bytes because the initial program had two 4-byte AArch64 instructions. The file offset identifies where bytes are stored inside the ELF file; VirtAddr and PhysAddr identify where the segment belongs in target memory. Program headers describe loadable segments, which is what an ELF loader uses.
17. Load boot.elf into QEMU
qemu-system-aarch64 \
    -machine virt \
    -cpu cortex-a53 \
    -m 512M \
    -nographic \
    -kernel boot.elf \
    -S \
    -gdb tcp::1234
The -kernel boot.elf option supplied the firmware image to QEMU. QEMU was again paused so GDB could inspect the CPU before execution.
gdb-multiarch
(gdb) file boot.elf
(gdb) target remote :1234
0x0000000040000000 in _start ()
(gdb) info registers pc sp
pc = 0x40000000
sp = 0x0
This was a major verification point: the ELF entry point was 0x40000000 and GDB showed the CPU PC at exactly 0x40000000 in _start. SP was still zero because the CPU had not executed the firmware yet.
18. Single-Step the Firmware
(gdb) stepi
(gdb) info registers x0 pc
x0 = 0x0
pc = 0x40000004
After mov x0,#0, x0 was zero and PC advanced by 4 bytes.
(gdb) stepi
(gdb) info registers x0 pc
x0 = 0x0
pc = 0x40000004
After b., PC remained at 0x40000004 because the instruction branches to itself.
(gdb) x/2i 0x40000000
(gdb) x/1i 0x40000004
0x40000000 <_start>:       mov x0, #0x0
0x40000004 <_start+4>:       b 0x40000004 <_start+4>
This connected source code, machine instructions, addresses, and CPU execution. GDB's arrow marks the current PC.
19. Verify RAM Before Stack Placement
grep -n -A5 "memory@40000000" virt.dts
20: memory@40000000 {
21-    reg = <0x00 0x40000000 0x00 0x20000000>;
22-    device_type = "memory";
23-};
The RAM information was rechecked before selecting the stack location.
20. Add Stack Initialization
nano start.S
.section .text
.global _start

_start:
    ldr x1, =0x5ff00000
    mov sp, x1

    mov x0, #0

    b .
A bare-metal firmware environment does not receive a process stack from an operating system. The firmware therefore initialized SP itself. 0x5ff00000 was selected near the top of the known 512 MiB RAM range and safely inside it.
The ldr x1,=0x5ff00000 form is assembler convenience syntax. The assembler implements it using a PC-relative literal load and a literal pool.
21. Inspect the Assembler's Literal Pool
aarch64-linux-gnu-gcc -c start.S -o start.o
aarch64-linux-gnu-objdump -d start.o
0000000000000000 <_start>:
   0:   58000081        ldr     x1, 10 <_start+0x10>
   4:   9100003f        mov     sp, x1
   8:   d2800000        mov     x0, #0x0
   c:   14000000        b       c <_start+0xc>
  10:   5ff00000        .word   0x5ff00000
  14:   00000000        .word   0x00000000
The assembler placed the 64-bit value 0x000000005ff00000 in a literal pool. The CPU loads that value into x1 and then moves it into SP.
22. Link the Updated Firmware
aarch64-linux-gnu-ld \
    -T linker.ld \
    -o boot.elf \
    start.o

aarch64-linux-gnu-readelf -h boot.elf | grep "Entry point"
aarch64-linux-gnu-objdump -d boot.elf
Entry point address: 0x40000000

0000000040000000 <_start>:
    40000000:   58000081        ldr x1, 40000010 <_start+0x10>
    40000004:   9100003f        mov sp, x1
    40000008:   d2800000        mov x0, #0x0
    4000000c:   14000000        b 4000000c <_start+0xc>
    40000010:   5ff00000        .word 0x5ff00000
    40000014:   00000000        .word 0x00000000
The linker moved the code and literal pool from section-relative offsets to their final addresses beginning at 0x40000000. The entry point remained 0x40000000.
23. Prove Stack Initialization with GDB
QEMU was restarted so it would load the newly rebuilt boot.elf. GDB loaded boot.elf before connecting to QEMU.
(gdb) file boot.elf
(gdb) target remote :1234
(gdb) info registers pc sp
pc = 0x40000000
sp = 0x0
The CPU was stopped before the first instruction.
(gdb) stepi
(gdb) info registers x1 sp pc
x1 = 0x5ff00000
sp = 0x0
pc = 0x40000004
The ldr instruction loaded the stack address into x1, while SP remained unchanged.
(gdb) stepi
(gdb) info registers x1 sp pc
x1 = 0x5ff00000
sp = 0x5ff00000
pc = 0x40000008
The mov sp,x1 instruction then initialized the stack pointer. This was directly observed at CPU register level.
24. UART and Memory-Mapped I/O
The lab identified the PL011 UART at 0x09000000. The UART is a memory-mapped device, meaning the CPU accesses its hardware registers using addresses in the guest address space.
CPU instruction
    |
    v
0x09000000 (PL011 register space)
    |
    v
UART hardware
    |
    v
QEMU serial output
A bare-metal program does not automatically have printf or an operating-system driver. Firmware must access the device registers directly or through firmware-level driver code. The UART identification therefore prepares the next firmware extension: a uart_putc routine and serial output.

26. Key Concepts
26.1 User Mode vs System Emulation
Lab 1 demonstrated an AArch64 Linux application. Lab 2 demonstrated bare-metal firmware on a complete virtual ARM machine. This is the main conceptual transition.
26.2 RAM vs Entry Point
RAM at 0x40000000 is a memory region. The entry point is the address where the executable begins. In this lab the linker deliberately placed the entry point at the RAM base, and QEMU loaded the ELF accordingly. These concepts must not be treated as universally identical.
26.3 Sections vs Segments
The source used a .text section, while the executable contained a LOAD program segment. Loaders use program headers to determine what should be placed in memory.
26.4 Stack
Bare-metal firmware must establish its own stack. The lab changed SP from 0 to 0x5ff00000 through two explicit instructions.
26.5 Memory-Mapped I/O
Hardware devices can appear at fixed addresses. The CPU interacts with such devices through loads and stores to those addresses. The PL011 UART is the concrete example in this lab.
26.6 GDB
GDB made the boot process observable. Instead of assuming that code ran, the lab measured PC, SP, registers, and instructions at each step.

28. Final Technical Outcome
The final output of Lab 2 is more than terminal text. The lab produced a working minimal AArch64 bare-metal ELF and demonstrated its complete path from source to execution:
source
  -> assembler
  -> relocatable ELF
  -> linker-controlled layout
  -> executable ELF
  -> QEMU loads image
  -> Cortex-A53 executes entry point
  -> firmware initializes stack
  -> firmware can interact with MMIO hardware
  -> GDB observes execution
The practical achievement is the ability to trace an instruction from source code through machine-code generation and ELF metadata, into a target memory address, and finally into actual CPU execution.

30. Final One-Paragraph Explanation
I built a minimal AArch64 bare-metal firmware for QEMU's virt machine. I first inspected the QEMU-generated Device Tree to determine the virtual Cortex-A53 CPU, RAM starting at 0x40000000 with 512 MiB, and PL011 UART at 0x09000000. I wrote an AArch64 assembly entry point, assembled it into start.o, and used a linker script to place the .text section at 0x40000000 and define _start as the entry point. readelf and objdump verified the ELF layout. QEMU loaded boot.elf, and GDB confirmed that the CPU PC was 0x40000000, matching the ELF entry point. Single-stepping showed the actual machine instructions executing. I then added stack initialization, loading 0x5ff00000 into x1 and moving it into SP, and GDB directly confirmed the transition from SP=0 to SP=0x5ff00000. The PL011 UART was identified as the next memory-mapped hardware interface. The lab therefore established the complete basic firmware model: source code becomes machine code, the linker assigns memory addresses and an entry point, QEMU provides the ARM machine, the CPU executes the firmware, firmware establishes its own runtime state, and hardware is accessed through memory-mapped registers.
